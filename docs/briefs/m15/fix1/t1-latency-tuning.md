**Part A: session fixes (do first; each is small).**
1. **Keep-alive.** WSL stops the distro when no Windows process is attached, which kills running sessions (Claude saw this on Nov 11). `tools/stream.sh up` must leave a detached keep-alive running for as long as any session runs (for example a background `wsl -d tp-stream -- sleep infinity` whose PID is kept in a file under the user's temp folder; `down` of the last session ends it; `status` shows whether it is alive). Kill only that PID, never another process.
2. **The player relay** (`streaming/player/serve.py`): its docstring says a page "can never reach the host's own API" while it relays four paths with the session's token. Correct the docstring to say exactly which paths are relayed and why; refuse every other path with 404; add a size cap on relayed bodies (64 KB).
3. **Bitrate honesty.** Find out why the bitrate setting is ignored: `webrtcsink` runs its own congestion control and sets the encoder's bitrate itself (see its `min-bitrate`, `max-bitrate`, `start-bitrate` and `congestion-control` properties). Make `SESSION_BITRATE_KBPS` the real ceiling (set webrtcsink's max and start bitrate from it), prove it with the bench's received bitrate, and fix the wording in `streaming/README.md` and the bench's run table.
4. The WSL distro is now in **mirrored networking** (the owner's `.wslconfig`, Nov 11): the distro has the PC's own LAN address. Check `tools/stream.sh url` prints the right addresses in this mode and correct `streaming/README.md` "Watching from another device" to match what is true now (the owner still adds the firewall rule; do not change anything on Windows).

**Part B: experiments.** First run the bench once unchanged as the baseline (`tools/stream.sh bench --sessions 1 --seconds 60 --game arena`). Then one change at a time, each run with the same bench, recording: stream_capture, stream_encode, stream_jitter_buffer, stream_decode, stream_display, stream_total, press_to_screen (median and p95), delivered fps, game fps, received bitrate, dropped frames, freezes, container CPU. Keep a change if it lowers press_to_screen or stream_total by more than the run-to-run noise (run the baseline twice to learn the noise) without adding freezes or drops; otherwise revert it. Suggested order (most promising first; add your own if the numbers point elsewhere):
1. **Video without audio sync.** Chrome holds video back to stay in sync with audio's larger buffer. Play the audio track and the video track from two separate `MediaStream`s / media elements in the player, so each has its own buffer. Measure the jitter buffer and the audio/video sync offset after (a sync error under 60 ms is acceptable for now; report it).
2. **No periodic keyframes.** A keyframe every second (`gop-size=60`) makes a burst the receiver must buffer for. Set an effectively infinite GOP with keyframes only on request (PLI/FIR from the receiver, which `webrtcsink` forwards), and intra-refresh if the element offers it.
3. **A one-frame encoder buffer.** Set the VBV/HRD buffer to one frame's worth of bits (bitrate / frame rate) and strict CBR, so no frame is much bigger than the others.
4. **The playout-delay header extension.** Ask the receiver for zero playout delay from the sender side (the `playout-delay` RTP header extension, min 0 max 0), if `webrtcsink` or the payloader can add it.
5. **Fixed bitrate, no FEC, retransmission on/off.** On a home network: `congestion-control=disabled` with the fixed bitrate, `do-fec=false`, and `do-retransmission` both ways.
6. **Steadier frame pacing.** Leaky one-buffer queues between capture, convert and encoder; check that the compositor produces frames on a steady clock (print the capture intervals' spread).
7. **The encoder's 30 ms.** It falls to 17 ms under load, so it is a wait, not work: try `nvcudah264enc` against `nvautogpuh264enc`, the converter placement (system memory vs CUDA upload), and the element's own latency properties.
8. **The game's 44.7 fps** (the probe had 57): find what costs the frames (the sampler, the stats posting, the test card, vsync against the virtual screen) by switching each off for a run.
9. **The host's own leg.** press_to_screen is 203 while stream_total is 126: measure where the other ~77 ms goes (press arrival → the game tick that uses it → the frame drawn → captured), record it as stages in the existing framework, and report what would cut it (for example the game ticking at 60 when drawing at 45).
