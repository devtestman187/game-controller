The owner's rule (Nov 11, 2026): "If there are any remote control feature (eg making the Linux scriptable or remotely controllable via an api), make that available to other builds as well to help with automated testing or making demo videos." Claude's design:
1. **One automation interface in `party_host`** (shared by the Windows, Linux, Android TV and phone hosts), **off by default**. It turns on only by an explicit switch: a runtime environment variable or command-line flag on desktop hosts (`THUMBPARTY_AUTOMATION=1` / `--automation`), a `--dart-define` for mobile builds. It is compiled into release builds but inert unless switched on, and **store builds never switch it on** (a test proves the default is off and that nothing listens). It listens on the loopback address only unless `THUMBPARTY_AUTOMATION_BIND` says otherwise (the container sets it so the sampler and the published port can reach it); an optional shared token (`THUMBPARTY_AUTOMATION_TOKEN`) is required on every request when set, and is required whenever the bind address is not loopback.
2. **A small HTTP + JSON API** (versioned path `/automation/v1/...`, documented in docs/automation.md with a curl example for each call):
   - `GET status`: app version, host type, screen/route now, whether a round is running, players (number, nickname, simulated or real), the pairing code, `ready` (true when the home screen is up and the host is listening);
   - `POST players`: add or remove **simulated players** (local players through the host's existing local-player path, S2), with a nickname and character;
   - `POST input`: a press/release or stick position for a simulated player (the same input shape controllers send), including menu navigation (so a script can drive every screen like a phone can);
   - `POST game/start`: start a game directly (game, mode, map, puzzle, level, teams, night rounds, settings such as Chaos and Robo's level) and `POST game/stop`;
   - `POST settings`: look (Sunny/Night), frame rate, sound on/off;
   - `GET state`: the current game snapshot (the same JSON a viewer gets) and the round's result when it ends;
   - `GET screenshot`: a PNG of the host's current frame where the platform allows it (desktop: yes; say what mobile can do);
   - `POST probe/flash`: show the **latency test card** (a full-screen block that flips between two colours and shows a frame counter and the host clock in ms) and `POST probe/press`: inject a press for a simulated player at a known host time, returning that time, so a viewer can time press → pixel change;
   - `POST stats/stream`: **the ingest endpoint** for the stream measurements of job p1 (viewer registration, stage samples, gauges, counters, resource samples in one batched JSON body), feeding the session collector; plus `GET stats/session` returning the current session summary (so a script can read the numbers without the upload).
3. **Replace the debug-only start flags** (`START_GAME`, `SHARE_VIEW`, `FRAME_RATE_HZ`) with thin wrappers over the same code paths the API uses, so there is one mechanism; keep the flags working for existing tools (tools/tv-dev.sh, tools/smoke.sh) and note them as deprecated in favour of the API.
4. **The latency test card screen** in shared host code, reachable from the API and (for the owner) from the TV's latency/stats screen.
5. **A script client**: `tools/automation.dart` (or .sh) with subcommands for the calls above, and one worked example: `tools/demo-run.sh` that starts a Bumper Round with two simulated players and takes a screenshot, as the seed for automated tests and demo videos.
6. Sessions made only of simulated players must be marked as such in the stats (so they never pollute real play data) and are never uploaded.
