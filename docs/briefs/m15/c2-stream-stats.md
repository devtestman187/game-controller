The owner (Nov 11, 2026): "I need to be able to measure the performance of streaming (audio, video and controller latency, cpu/memory usage of the containers, and anything else you think will be useful)", through the existing stats framework. Jobs p1 (schema, report), a2 (ingest endpoint, probe, automation) and c1 (the container and player) are in. This job connects them:
1. **The container starts the game with automation on** (bound so the in-container sampler and the published port reach it, with a token generated per session and passed to the player page), and waits for `status.ready` before reporting itself ready.
2. **The web player reports** (batched every few seconds to `stats/stream` through the container's web server or the automation port, with the token): from `RTCPeerConnection.getStats()` and `requestVideoFrameCallback`: jitter-buffer delay, decode time, frames received/decoded/dropped, freezes, resolution, frame rate, bitrate, packet loss, round trip, jitter, NACK/PLI counts, time to first frame, reconnects, relay or direct, codec; presentation delay per frame (`stream_display`); the same for sound (jitter-buffer delay, concealed samples) and the audio/video sync offset. A clock offset between player and host is kept with a small ping over the same channel (as the controller protocol does), so cross-device stages can be computed.
3. **The host side reports**: capture and encode times per frame from the pipeline (GStreamer latency tracer or buffer timestamps around `waylanddisplaysrc`, the converter and the encoder; sender stats from `webrtcsink`: bitrate, frames encoded, keyframes), the game's own frame rate and frame times, and a **sampler** in the container (a small script or Dart program) sending every 2–5 s: CPU % and memory of the container from cgroup files, split by process where cheap (game, pipeline, PulseAudio), GPU %, encoder % and GPU memory from `nvidia-smi`, encoded frame rate, and how many sessions run on the machine. If a per-frame network stage is feasible with an RTP header extension (abs-capture-time or similar) through `webrtcsink` and the browser, use it; otherwise use round trip / 2 and say so in the data.
4. **Press-to-screen, measured, not summed**: the player watches a small region of the video (a canvas sample inside `requestVideoFrameCallback`) for the latency test card's flip; the benchmark calls `probe/flash`, then `probe/press` N times (random gaps); each press's host time and the player's presentation time (offset-corrected) give `press_to_screen` minus the controller's own network leg; record it as its own series and note what it does and does not include. Do the same for sound if the probe can make a click on the press (audio onset detection with an AnalyserNode), giving a measured `audio_capture_to_play`.
5. **`tools/stream.sh bench [--sessions N] [--seconds S] [--game arena|shape_race]`**: builds if needed, starts N sessions, opens a headless browser viewer for each inside the distro, uses the automation API to add simulated players and play a round (inputs from a simple script so the picture moves), runs the press probe, stops, pulls each session's summary from `stats/session`, saves them under a results folder in the distro, fetches a compact results file into docs/briefs/m15/c2/, and prints the report's Streaming section for them (run the report tool on the saved summaries). Also `tools/stream.sh stats` for a running session.
6. **Run it** and put the results in the report: one session (60 s, Arena Bumper Round, then Shape Race), two sessions at once, and one session at 720p for comparison: every stage's median and p95, press-to-screen, sound delay and sync, bitrate and drops, CPU and memory per container, GPU and encoder use, time to ready. State plainly which numbers are measured, which are derived, and which are missing and why. Compare with the capture probe's numbers (docs/briefs/m15/capture-probe-report.md) and flag anything that got worse.
8. **From job c1's findings (Claude's decisions, Nov 11, 2026):** the entrypoint sets `THUMBPARTY_PORT` to the session's controller port and `THUMBPARTY_STATS_CONSENT=no` (both added by job a2), and drops the port-discovery workaround if the pinned port makes it unneeded. c1 measured a **jitter buffer of 96–140 ms** on a 1 ms round trip and 55 fps for one session, 31 fps each for two: these are the numbers to explain. Record the jitter buffer as its own stage, and in the bench also run one session with the player's jitter-buffer target forced to its minimum and one with the compositor and encoder at 720p, so the report shows what each buys. `stream_network` is the viewer's round trip / 2 unless the per-frame header extension works. The resources tables get a p95 column for CPU, memory and GPU (the JSON already has it).
7. **Tuning notes, not tuning**: list the three settings most likely to cut delay next (with the measured stage each would reduce); change nothing beyond what is needed to measure.
