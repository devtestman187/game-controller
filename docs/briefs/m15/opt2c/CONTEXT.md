# opt2c: shared context for every job of this batch (read it first, whole)

Game-streaming project. A Linux session image (WSL2 distro tp-stream) captures a game, encodes H.264 1080p60 CBR (nvautogpuh264enc, ~9.3 Mbit/s video, gop 60 frames) and sends it with webrtcsink; with `SESSION_TAP=on` a tee also feeds streaming/tap/tap_runner.py (appsink -> tap_server.py, one thread and a 4-frame queue per client, WebSocket frames, PROTOCOL.md in docs/briefs/m15/opt2/). The phone reaches it through the player relay streaming/player/serve.py (a byte tunnel on the player port, path /tap, to the tap server on loopback). The page `?player=wc` (streaming/player/wc_*.js) decodes with WebCodecs and draws on a canvas.

## What happened (iPhone Safari, LAN Wi-Fi, Nov 13, 2026, second sitting)
Press-to-screen card/marker ms, four runs: 167/152 (1 freeze); 149/133 with 7 freezes, 680 dropped, 15 keyframe requests, 14-21 Mbit/s received against the 10 Mbit/s ceiling; 121/84 clean (0 dropped, backlog 2); 251/241 with 9 freezes, 1062 dropped, 68 keyframe requests. Diagnosis (to verify, not proved): a keyframe storm. Frames back up, the sender drops to a keyframe, each drop/gap asks for another keyframe, big keyframes feed the backlog. A strong suspicion about WHERE the first backlog hides: the tunnel's phone-side socket has an auto-tuned send buffer of megabytes, and the tap server's socket to the tunnel is on loopback and never blocks, so the sender never sees a stall and delay grows silently (bufferbloat) until the page drops.
Headless proof baseline (this host, `tools/impair.sh`, netem on 127.0.0.2): stalls of 200-500 ms every 3 s for 30 s gave 205 dropped, 9 keyframe requests, 7-8 freezes (3.2-3.8 s); loss 1% + 12 Mbit cap + stalls gave 180 dropped, 10 keys, 7 freezes. Results docs/briefs/m15/bench-results/20261113-1448*, -1450*.

## Rules for every job
- decide: low-usage mode: never stop for a question. Make the safest choice that fits the design and list each under "Decisions" with one line of why. Stop only if the job truly cannot be done; then say why under "Blocked".
- Report starts with `## Summary` (at most 25 lines, in its first 40 lines): what was built (files), tests and results, decisions, not done, obstacles (one line each), turns if known. Ends with `## Hand-over` (at most 20 lines).
- Aim for about 100 turns (hard target 150). No lib or script file you touch may end over 380 lines (split it; the runner stops otherwise; serve.py is at 381 and tap_server.py at 370 now: any addition goes into a new module) and no function over 60 lines. Tests first: each new test file must fail on the code as it was; a behaviour change gets a failing test first. Existing tests stay green.
- Python passes `python3 -m py_compile`; scripts `bash -n`. Install nothing, download nothing. Never `wsl --shutdown`. Touch only processes you started, by PID. Wrap long commands in `timeout`. Leave NO scratch file behind (temp files in /tmp in the distro, deleted afterwards; none in the repository outside allow:).
- Every switch defaults OFF (the tap itself is off by default; with SESSION_TAP off nothing changes). Never touch E:\AI\game-controller. Never print the DeepSeek key.
- No `tools/stream.sh up`/`build`, no bench with `--viewer external`. Tests run in the distro tp-stream (`wsl: tp-stream`): sync with `tools/wsl-sync.sh tp-stream` and work in the copy it prints; `python3 streaming/tap/tap_server_test.py`, `python3 streaming/player/relay_test.py`, `timeout 150 bash streaming/bench.sh --selftest` (page tests; wc pages are listed in run_page_selftest of streaming/bench.sh). A new Python test file must be added to `cmd_selftest` in tools/stream.sh; a new page file the relay serves must be added to `page_files` in streaming/player/serve.py (relay_test checks every import is served). Dart: `tools/check.sh format` on Windows.
- Stay inside `allow:`.
