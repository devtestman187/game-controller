Problem: on the phone, frames back up, the sender drops to a keyframe and asks for one, the page drops deltas and asks again, every client message `{"type":"key"}` goes to the encoder at once, and each IDR is large; 68 requests in a 60 s run, 14-21 Mbit/s against the 10 Mbit/s ceiling. The stream has a natural IDR every gop (60 frames = 1 s), so a client waiting for a keyframe never waits longer than about 1 s without asking at all.

Design (tests first for each item; new test files allowed):
1. Host, per client (tap_queue.ClientQueue): at most ONE key request outstanding per client: it is set when a request is made and cleared when a keyframe is queued for that client or after KEY_OUTSTANDING_TIMEOUT_S = 2.5; the same client never asks the encoder again sooner than KEY_MIN_SPACING_S = 1.5 after its last ask. `_clear_to_keyframe` while the client already needs a keyframe asks nothing. The first ask on connect stays. Counters: `keyreq` counts asks actually made; add `keyreq_suppressed`.
2. Host, encoder side (tap_runner.request_key_unit): same rule across all clients: one outstanding until a keyframe leaves the encoder (seen in _on_new_sample) or 2.5 s pass; at least 1.5 s between force-key-unit events (replace the 200 ms constant). Clients' messages `{"type":"key"}` go through the client's own rule (item 1) and then this one.
3. Page (wc_player.js, wc_decoder.js if it asks too): keyRequestMinMs 500 -> 1500; one outstanding: no new request until a keyframe message has arrived or 2500 ms have passed; while waiting, deltas are dropped quietly (as now) without another request; a decoder error still asks, through the same rule. Counters keep their names; add `keyRequestsSuppressed`. Page test in a new wc_keys_selftest.html (added to run_page_selftest in bench.sh, fake WebSocket and clock): 20 gap events in 1 s send one request; a request is repeated only after 1.5 s without a keyframe.
3b. THE ROOT CAUSE (read docs/briefs/m15/opt2c/EVIDENCE.md first): after a stall the burst of frames makes `_handleFrame` see decoder queue > maxQueueDepth (2): it drops that delta and asks for a keyframe, and every later delta then fails `frame !== lastFrame + 1` and is dropped until the next IDR (about 22 frames per 300 ms stall). Replace it with CATCH-UP: a delta is decoded whenever the chain is intact (queue depth is no reason to drop it); the decoder output callback draws a frame only when it is the newest the decoder holds (decodeQueueSize 0, or the next input not yet decoded), otherwise it closes the VideoFrame without drawing (counter `skippedDraws`, shown in the wc table and sent as a gauge only if a gauge slot is free: the host keeps 16 gauges per viewer and the page already sends 16; if none is free keep it in counters()). Only a decoder queue over HARD_QUEUE_FRAMES = 40 (truly overloaded) falls back to drop + keyframe request (through the spaced rule). The freeze rule (a draw gap over 150 ms) is unchanged. Tests first with a fake VideoDecoder: a burst of 25 deltas after a 400 ms gap decodes all 25, draws the newest, requests no keyframe and drops nothing; a queue of 41 drops and asks once.
4. Decision to record, no code: serving a recovering or late client from the most recent keyframe plus the following deltas is NOT built: it is a burst of up to 1 s of old video that is itself a backlog, and the natural IDR is at most 1 s away; say so under Decisions.
5. Encoder rate control on the tap path (streaming/entrypoint.sh, only when SESSION_TAP=on and SESSION_VBV_KBITS is 0): give the encoder `vbv-buffer-size` = video_kbps * 3 / frame_rate (about three frames' worth, ~470 kbit at 9.3 Mbit/s and 60 fps; override by new SESSION_TAP_VBV_KBITS), with strict-gop=true as the existing SESSION_VBV_KBITS branch does. Check in tp-stream with `gst-inspect-1.0 nvautogpuh264enc` and a short real encode (videotestsrc or the existing pipeline words in the Hand-over of docs/briefs/m15/opt2b/f2-nv12-report.md) that the element accepts it and the IDR size drops; report key KB before and after. The installed encoder has NO intra-refresh or gradual-decoder-refresh property (checked: only aq, gop-size, min-force-key-unit-interval, repeat-sequence-header, strict-gop, vbv-buffer-size, max-bitrate (ignored in CBR)); say that, do not look further.
