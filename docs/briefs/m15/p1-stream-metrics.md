The owner (Nov 11, 2026): "ensure the necessary metrics are in place using the existing stats reporting framework. I need to be able to measure the performance of streaming (audio, video and controller latency, cpu/memory usage of the containers, and anything else you think will be useful)". This job builds the data model, collector API and report; later jobs feed it (a2: the host's ingest endpoint; c2: the web player and the container's sampler). Claude's design:
1. **A session-level `stream` record** in the session summary (additive, schema stays readable by old reports; old sessions simply have none), holding one entry per viewer (a screen showing the stream; it has a short id and a kind: browser, app, its platform string cleaned like device strings are today) and one host/container entry. Nothing personal: no IP addresses, no user-agent strings beyond a cleaned short platform name.
2. **Video stages per viewer**, each summarised like today's stages (n, median, p95, max) and also by frame rate where that applies: `stream_capture` (frame drawn → captured), `stream_encode` (captured → encoded), `stream_send` (encoded → on the wire), `stream_network` (one-way estimate; note in the docs how it is derived, e.g. round trip / 2), `stream_jitter_buffer`, `stream_decode`, `stream_display` (decoded → presented), plus the derived **`stream_total`** (capture → presented) and **`press_to_screen`** (a controller press → the frame showing it on the viewer: measured by the automated probe of job c2 when available, otherwise the sum of the stages with today's `sent_to_received` and `received_to_drawn`; say which in the data).
3. **Sound per viewer**: `audio_capture_to_play` (or its parts if known: encode, network, jitter buffer), audio/video sync offset (ms, signed), concealed/lost audio share.
4. **Controller**: today's stages stay as they are; add nothing here except that the report's streaming table shows them beside the stream stages for the same session, so one row reads input → host → encode → network → decode → display → total.
5. **Network and quality per viewer** (counters and gauges sampled over time, summarised as mean/p95/max where it makes sense): bitrate sent and received, frames sent / received / decoded / dropped / late, resolution and frame rate delivered, packet loss %, round-trip time, jitter, NACK / PLI / FIR counts, keyframes, freezes (count and total ms), time to first frame, reconnects, whether a relay (TURN) was used, codec, encoder name.
6. **Container / host resources** (sampled every few seconds while a session runs; summarised mean/p95/max, plus the samples' count): CPU % of the session (all processes in the container, and the game and the encoder pipeline separately when given), memory (RSS/cgroup current and peak), GPU % and encoder %, GPU memory, the game's own frame rate and frame build/raster times, encoded frame rate, encode queue depth, session start time (cold start to first frame ready), and the number of sessions running on the machine at the time.
7. **Collector API** in packages/metrics: methods to register a viewer, add a stage sample, add a gauge sample, set a counter, add a resource sample; bounded memory (cap samples per series like stages are capped today); unknown series names are kept (forward compatible) with a length limit, as stage names are.
8. **Report**: a new **"Streaming"** section in the CLI report: (a) one row per session and viewer with the stage medians and p95s in pipeline order and the totals; (b) quality (bitrate, loss, drops, freezes, time to first frame); (c) sound; (d) resources per session and by "sessions at once" (so capacity shows: 1, 2, 3 sessions); and matching CSV columns or a second CSV. Sessions without a stream record are left out of this section. Follow the existing table style; document each column in the report's help or docs.
9. **Docs**: docs/protocol.md or the metrics doc gets the `stream` record's fields and units; docs/PRD-v2.md S7 gets one line naming the new stages (do not rewrite the PRD).
