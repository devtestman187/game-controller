Design:
1. streaming/tap/tap_server.py (stdlib only: socket, threading, hashlib, base64, struct; no new package): a WebSocket server on 127.0.0.1:TAP_PORT. RFC 6455 server side: handshake (Sec-WebSocket-Accept), read masked client frames (text, ping, pong, close, fragmented text allowed), write unmasked binary/text/ping/close frames, TCP_NODELAY. One thread per client plus the producer calling `publish(frame_no, pts_us, is_key, data)` from the appsink callback (non-blocking: it only appends to each client's bounded queue and notifies). The messages are exactly PROTOCOL.md (hello on connect, binary frames, `{"type":"end"}`, client `{"type":"key"}`).
   Backlog policy per client (all in a pure class `ClientQueue` that is unit-tested without sockets): at most 4 frames queued; a client that has not drained within that, or whose socket write would block for more than 50 ms (use a send timeout on the socket), is dropped to "needs keyframe": its queue is cleared, non-key frames are not queued until a keyframe, a keyframe is requested through `request_key_unit()`, and the first frame after carries flag bit1 (discontinuity). A new client starts in "needs keyframe" and a keyframe is requested at connect. `sent_us` is taken when the thread writes the frame (time.time()*1e6). Counters per client and total (frames sent, frames dropped, keyframe requests, queue high water, bytes) exposed as `stats()` and logged once every 5 s to stderr as one line `tap: clients=N sent=… dropped=… keyreq=…`.
2. Wire it into tap_runner.py (small edit: start the server with --port, publish from the appsink callback, request_key_unit as the server's callback, `end` message and shutdown at EOS).
3. serve.py: a GET with `Upgrade: websocket` on path exactly `/tap` is tunnelled: connect to 127.0.0.1:tap_port (new argument `--tap-port`, default 0 = off, in which case /tap answers 404 as every unlisted path does), forward the request head, then pump bytes both ways with two threads until either side closes; TCP_NODELAY on both sockets; the relay adds no buffering beyond one socket read (64 KB) and never reads the body of a frame. Only /tap, GET, with the upgrade header, is tunnelled; nothing else of the relay changes; the "nothing else answers" rule and the docstring list stay true (add /tap to the docstring list and the tunnelled-only-to-loopback-tap-port statement). Add the page files wc_annexb.js, wc_player.js, wc_stats.js to `page_files` (they are written by other jobs; a missing file just 404s). The entrypoint passes `--tap-port "$tap_port"` to serve.py only when SESSION_TAP=on (tap_port is already computed by job 1; check its name in the report).
4. Reach: the phone already reaches the player port, so no new port and no firewall rule: state this in the report. Do not change any Windows setting.
