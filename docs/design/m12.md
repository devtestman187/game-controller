# M12 design: phone-hosted play

Nov 6, 2026 · approved by the owner (decisions in section 6). Requirements: PRD v2 C25 to C29, C34, S1 to S9, the "On phones" part of the puzzle design, and the non-functional rows for phone-hosted delay, frame rate, battery and heat. Coding rules: [coding-guidelines.md](../coding-guidelines.md).

## 1. What the code already gives us, and what blocks phone hosting

Ready (M9 to M11 did the groundwork):
- `GameHost` (P3) is pure Dart, and both games use only it. `MemoryGameHost` exists for tests.
- Both games keep rules apart from drawing and have versioned JSON snapshots: `MatchSnapshot` (carries the split layout's seed and draw order, under 2 KB for 4 players) and `ArenaSnapshot`.
- Local players (S2), game-defined controls (P5), the status panel (P6), capabilities (P2), `role` and the reserved `view` capability (S3), named latency stages (S7).
- `InputStateMessage` carries `seq` and `ts`, and the host estimates each phone's clock offset.

Blocking, and fixed by this design:

| # | Problem today | Why it blocks M12 |
| --- | --- | --- |
| B1 | The whole host stack (server, advertising, stats, game picker, join, play, pause, results, Puzzle settings, Stats, consent, sound, controller menus) lives in `tv_test_app` | The phone app can't host without copying it. Copies drift |
| B2 | `HostServer` and `ControllerClient` are built on `WebSocket` directly | The host phone's own player has no clean path in; it would need a special case or a socket to itself |
| B3 | `LocalPlayer` only takes input: `haptic`, `setLayout`, `setStatus` and `askRating` return false or do nothing for it | The host phone's player would get no haptics, no labels, no rating |
| B4 | `PuzzlePlayView` and `ArenaView` run the game loop inside the widget, on a variable `dt` | A joined phone needs the view without the loop; snapshots need a steady, deterministic host tick |
| B5 | `ControllerScreen` owns the whole screen, with an opaque background and the status panel in its top bar | Controls can't sit over a game view (S9) |
| B6 | `SplitLayout` puts the tray beside or below the board for a TV screen | The PRD wants the tray along the top edge, each phone zoomed to its own side |
| B7 | Discovery's TXT records don't say what kind of device hosts | Phones can't be labelled as phones in the host list (C26) |

## 2. Architecture

```
                     ┌──────────────────────── controller_app ───────────────────────┐
                     │  Controller mode      Host mode            Joined-view mode   │
                     │  (as today)           party_host +         FrameView +        │
                     │                       ControlsLayer        ControlsLayer      │
                     └───────────┬───────────────┬──────────────────────┬────────────┘
 tv_test_app (shell) ──────────► party_host (NEW, Flutter): HostService, host screens, sound, stats
                                       │
                         game_kit (NEW, Flutter): GameModule registry, GameSession, FrameView, playout
                                       │
                 puzzle_game, test_game (rules + views; sessions split from views)
                                       │
         connection (pure Dart): Transport + InProcessLink, HostServer, ControllerClient,
                                 GameHost (+ frames, + local controller endpoint)
                                       │
                          protocol (pure Dart): + view_start, frame, view_end, stages
```

### 2.1 Transport (fixes B2)
- `connection` gets a `MessageChannel` interface (send text, incoming stream, close with code, done). `WebSocketChannelAdapter` wraps today's socket; `InProcessLink` gives a connected pair of channels in memory.
- `HostServer` takes channels from any number of `ChannelListener`s (the WebSocket listener, and an in-process listener). `ControllerClient` takes a `Connector` (WebSocket by address, or in-process). Pairing, tokens, heartbeats and close codes stay exactly as they are, for every channel.
- An in-process channel is marked `local` on the server, and its player is reported as `GamePlayer.local`, so analytics show "watched on the host phone".

### 2.2 The host phone's own player (fixes B3)
**Decision D1: the host phone's player is an ordinary `ControllerClient` over an `InProcessLink`**, with the same identity, capabilities, metrics, haptics, layout, status and rating as any joined phone. It pairs with the host's current code, as the TV's simulated controllers already do, so pairing has no special path either. Why: every controller feature works on the host phone with no special case, and the code path is the one already tested. The in-memory hop costs microseconds. `LocalPlayer` stays for the Windows keyboard player.

### 2.3 Game sessions and frames (fixes B4)
Step 3's contract, [m12-sessions.md](m12-sessions.md), refines §2.3 to §2.5 and §3, and wins where they differ. It drops `createSession` from `GameModule`, has each game package export its module, adds the roster (`pl`) to frames, puts the stage samples in the metrics batch, and replaces `frame_received` with `frame_jitter`.
- New package `game_kit` defines `GameModule`: `id`, `snapshotVersion`, `createSession(GameHost, GameSetup)`, `decodeFrame(json)`, and `buildView(frame, ViewSpec)`. A `GameRegistry` holds Shape Race and Arena. Nothing switches on a game ID.
- `GameSession` (pure Dart) owns the loop: an accumulator advances the rules in fixed steps of `simStepS` = 1/60 s, turns events into haptics, sounds and records through `GameHost`, and produces the current snapshot. `PuzzlePlayView` and `ArenaView` become thin widgets: a `Ticker` feeds elapsed time to the session and draws its snapshot. On a TV nothing visible changes.
- **Frames.** After each step the session hands `GameHost.publishFrame` a `GameFrame`: the step number, the host's clock, the snapshot JSON, the sound names played in that step, and each player's last applied input `seq`. The host sends frames only to controllers that listed `view`.
- **Sounds (S5, C27).** On a TV the host plays them as today. In a phone-hosted game every phone, the host included, plays them from its own copy when it draws the frame that carries them. Haptics stay per-player messages.

### 2.4 Showing the game on a joined phone (C27)
- `view_start` tells a viewer which game module, its `GameSetup` (for the puzzle: puzzle ID, level, seed, teams, layout target) and the frame rate. The viewer checks the module and snapshot version, and shows "Update the app" on a mismatch. Every phone has the same puzzle files.
- **Playout buffer.** The viewer keeps the last few frames by host time and draws at `latest host time - playoutDelayMs`, interpolating positions and angles between the two frames around that time (`Interpolator` per snapshot type, rule-free: lerp positions, shortest-arc angles, no interpolation for discrete state). `playoutDelayMs` adapts to the measured arrival jitter (its 95th percentile), clamped to [0, `maxPlayoutFrames`] frame intervals. A gap longer than the buffer holds the last frame; it never extrapolates past a frame.
- `view_end` returns the phone to controller mode (results and menus are shown on the host's screen and mirrored, see 2.6).

### 2.5 Latency (S7) and the frame rate
**Decision D2: frames go out at 60 a second by default, not the PRD's proposed 30.** The budget, median case on home Wi-Fi:

| Stage | 30 frames/s | 60 frames/s |
| --- | --- | --- |
| Touch to input sent, network to host | ~4 ms | ~4 ms |
| Waiting for the next sim step | ~8 ms | ~8 ms |
| Waiting for the next frame send | ~17 ms | ~8 ms |
| Network to the joined phone | ~3 ms | ~3 ms |
| Playout delay (about one interval) | ~33 ms | ~17 ms |
| Drawing | ~8 ms | ~8 ms |
| **Total** | **~73 ms** | **~48 ms** |

At 30 a second the 50 ms target can't be met with smoothing. 60 a second is about 120 KB/s per joined phone (2 KB frames), well within Wi-Fi, at some battery cost on the host. The rate is a hosting setting (`frameRateHz`, 20 to 60), so the battery and heat check can trade it down. Step 3 measures this on real devices before anything else is built on it.

**Decision D3: touch-to-frame is measured without clock sync.** Each frame carries each player's last applied input `seq`. The joined phone knows when it sent that `seq` (its own clock) and when it drew the frame (its own clock), so `touch_to_frame` is exact. It also reports `frame_received` (host time to arrival, through the clock offset the phone estimates from pings, as the TV does). It also counts frame gaps (a missing step range) and late draws, which the PRD's analytics ask for. The phone sends these to the host inside its metrics batches, so they land in the session summary.

### 2.6 Host mode on the phone (C25, C29, C34)
- `party_host` holds what moves out of `tv_test_app` (B1): `HostService` (server, advertising through an `Advertiser` interface, the game host, stats, sound), and the screens: game picker, difficulty, join, play, pause, results, Puzzle settings, Stats, consent. `tv_test_app` keeps its home screen, test tools and TV-only parts, and uses `party_host` for the rest. No behaviour change on the TV; its tests must pass unchanged.
- On the phone, "Host a game" starts a `HostService`, connects the phone's own controller over the in-process link (D1), and shows the `party_host` screens with the controls on top. The screens already work by touch, remote focus and controller menus, so the host phone's owner can use either.
- **Show on this device (C34)** is a host option: the game fills the screen like a TV, with no controls on top and no own player; everyone uses their phone as a controller.
- **Host-side data (C29, S6):** consent, stats, best times and playtest settings come with `party_host`. `HostType` gains `phone` and `tablet`. The summary adds the host's battery drop and thermal states, sampled from the phone's existing `deviceStatus` channel behind a `DeviceMonitor` interface. Each player's record says where they watched: the host's screen, the host phone (in-process player) or a joined phone (listed `view`), so the report can compare TV play with phone play.

### 2.7 Controls as a layer (S9, C28; fixes B5)
- `ControllerScreen` is split into `ControlsLayer` (the controls of the current mode, transparent background, hit-tested only on controls) and the screen around it. `ControlsLayer(opacity)` draws over any child; controller mode passes an empty child and full opacity.
- The opacity setting (20% to 100%, default 60%) is saved with the other settings. Sizes and touch areas don't change with opacity (C14 to C16), and game-defined labels still apply.
- While a game is shown on the phone, the status panel is hidden.

### 2.8 The puzzle on a phone (fixes B6)
**Decision D4: the layout target is chosen when the match is created, and every screen shares it.** `SplitLayout` takes a `LayoutTarget`: `screen` (TV, PC, or C34, as today) or `phones` (per side: board in the middle, tray along the top edge, sized to the phone aspect ratio). The world is the same for every viewer, so the host, joined phones and tablets agree on where every piece is.
- A joined phone's camera (`SideCamera`) frames its own side's board and tray, with the clock and the other side's progress in a strip along the top ("Right 3/6"). A solo player sees the whole board. A tablet (by its physical size) shows the full split screen.
- **Minimum piece size:** a test checks every puzzle at the smallest supported phone (from the M7 device table) and fails if an Easy or Medium piece draws under `minPieceMm` (9 mm). Hard puzzles stay playable on phones; the test reports their smallest piece in millimetres (owner, Q4).
- The Arena shows the whole field on every phone, with the same layer of controls.

### 2.9 Discovery and labels (C26; fixes B7)
The host's TXT record gains `kind` (`tv`, `pc`, `phone`, `tablet`). The phone's host list shows phones as phones. Older hosts without `kind` show as today. iOS needs the Bonjour declaration to cover advertising.

### 2.10 Host interruptions
- The host phone's app lifecycle drives a `HostPresence`: when it goes to the background or locks, the game pauses at once, and joined phones show "Waiting for host" with a countdown of `hostGraceS` (30 s). Back within the grace period, the host resumes the round and re-sends `view_start` and the latest frame. After the grace period the round ends with no winner, recorded as `abandoned`.
- iOS may close the listening socket while the app is in the background. On resume `HostService` checks the server and restarts it on the same port if needed; phones reconnect with their tokens (the existing backoff). This needs a device check early (step 5).
- A joined phone that drops rejoins as with a TV, and gets `view_start` and the latest frame.

## 3. Protocol additions (all behind the `view` capability)

| Message | Direction | Fields |
| --- | --- | --- |
| `view_start` | host → viewer | `game` (module ID), `sv` (snapshot version), `setup` (module-defined JSON), `hz` (frame rate) |
| `frame` | host → viewer | `n` (step), `at` (host ms), `s` (snapshot JSON), `snd` (sound names, optional), `acks` (player number → last applied input seq) |
| `view_end` | host → viewer | `reason` (`finished`, `quit`, `abandoned`) |
| metrics batch, new field | viewer → host | `stages`: `frame_received` and `touch_to_frame` summaries (count, median, p95, max) |
| TXT record | discovery | `kind`: `tv`, `pc`, `phone`, `tablet` |

The protocol version stays 1: everything is additive.

## 5. Steps

Each step ends with `tools/check.sh` passing and a commit. In each step Claude writes the contract (types, signatures, doc comments, the brief and the test cases) and the worker writes the implementation and tests. Claude reviews every diff.

| Step | What | Owner of the contract | Exit check |
| --- | --- | --- | --- |
| 1 | **Extract `party_host`** from `tv_test_app` (move map, no behaviour change) | Claude: the move map and public API | Every existing TV test passes unchanged; the Windows build runs |
| 2 | **Transport** (`MessageChannel`, `InProcessLink`, listeners, connectors) | Claude: the interfaces | All connection tests pass on both transports |
| 3 | **Sessions, frames, playout, stages** (`game_kit`, `view` messages); then a latency measurement on the emulator and both phones | Claude: `GameModule`, `GameSession`, `GameFrame`, the messages | Measured touch-to-frame median under 50 ms, or an owner decision on D2 |
| 4 | **Controls layer and opacity** (S9, C28) | Claude: the `ControlsLayer` contract | Layout tests in all three modes at every opacity; no control smaller |
| 5 | **Host mode** (C25, C29, C34): HostService on the phone, in-process own player, advertising with `kind`, consent and stats, host interruptions | Claude: `HostPresence`, the iOS and Android advertising (platform code) | Solo puzzle on one phone with Wi-Fi off; lock and unlock within 30 s resumes |
| 6 | **Joined view** (C26, C27): host list labels, `FrameView`, Waiting for host, sounds | Claude: the view lifecycle | Two devices: one hosts, one joins and sees its side |
| 7 | **The puzzle on phones** (`LayoutTarget.phones`, `SideCamera`, top strip, 9 mm check) and the Arena on phones | Claude: the layout rules | Size test for every puzzle; widget tests on phone and tablet sizes |
| 8 | **Battery, heat and the report** (host type, device monitor, stage comparison of TV and phone play) | Worker from Claude's brief | Report prints TV vs phone tables from a test session |
| 9 | **Docs and device tests**: protocol.md, architecture.md, tester guide ("No TV? Host on a phone"), `checklists/m12.md` | Worker drafts, Claude edits | Owner runs the M12 device tests |

Steps 2 and 4 don't depend on each other and can run in parallel; everything else is in order.

## 5a. Review gates

Every step is split into gated jobs. A job ends at its gate: the worker stops, reports, and does nothing more. Claude reviews the diff and the checks; the next job starts only from Claude's approval, with Claude's corrections written into its brief. The worker's suggestions and questions go to Claude, who decides.

| Gate | What the worker has done | What Claude checks before approving |
| --- | --- | --- |
| G1 Plan | Read the brief and the code; reports the files it will touch, the order, and any conflict with the brief. No code | The plan matches the contract; questions answered |
| G2 Contract and tests | The public types and signatures from the brief, and the tests from the brief's cases (failing, or not compiling past the stubs) | Tests check the rules as written; names and layers are right |
| G3 First slice | One path through, end to end (for example, one game or one transport), with its tests passing | Structure, sizes and guideline compliance, before the pattern is repeated |
| G4 Complete | Everything in the brief, every check passing | The whole diff; then Claude commits |

Small jobs (one module under about 150 lines) may go straight from G2 to G4. A job that moves or splits existing files gets a G1 plan unless Claude's brief gives the move map or the seams are named and the job is a pure move; then it goes to G4, proven by `tools/review.sh --strings` (no text changes) and unchanged test counts (owner, Nov 6: evaluate "what can be done more efficiently").

- **Q1. `demo-video` is frozen** as it is: no more commits, and no merge into `main`. `party_host` moves the TV screens freely.
- **Q2. 60 frames a second** by default (D2), confirmed by step 3's measurement.

- **Q4. Hard puzzles stay available on phones.** The size test requires 9 mm for Easy and Medium, and reports Hard's smallest piece in millimetres without failing.
- **Q5. The flash-worker implements everything, protocol and connection included,** from Claude's contracts, and stops at review gates (section 5a). Claude is the source of truth: the worker may suggest or ask, and Claude decides.
- **Q6. Briefs may go to DeepSeek.** The repository is public.
